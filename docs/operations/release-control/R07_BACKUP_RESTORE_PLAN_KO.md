# R07 운영 백업·복원 검토안

상태: **차단**. 2026-11-28 기준 운영 DB의 사용 가능한 백업 파일·복원점과 운영 데이터 복원 성공 증거를 확인하지 못했다. 외부 보관본이 절대 없다고 단정하지 않는다. 운영 데이터 내보내기, 복원, 유료 서비스 변경은 수행하지 않았다.

## 확인 결과

- 운영 Supabase `Reballlostball`의 Scheduled backups 화면은 FREE 플랜에 프로젝트 백업이 포함되지 않는다고 표시한다. Point in time 화면은 Pro 플랜 부가 기능이라고 표시한다. Restore to new project 화면은 Pro 이상과 물리 백업 활성화가 필요하다고 표시한다. 기존 복원점을 선택하거나 실제 복원 가능하다는 증거는 얻지 못했다.
- 네 개의 리볼 작업 폴더에서 DB 덤프 확장자 이름을 제한적으로 검색했지만 찾지 못했다. Google Drive에서 프로젝트명·프로젝트 참조로 검색한 결과도 없었다. 프로젝트 기록의 과거 로컬 `pg_dump` 복원은 폐기용 시험 DB의 리허설이며 운영 데이터 복원이 아니다.
- 운영 DB의 논리적 크기는 약 71.7MB이고 Storage는 버킷 1개·객체 0개로 집계됐다. 이 숫자는 관측 시점 기준이고 외부 자산이나 설정 백업을 뜻하지 않는다.
- 로컬 Docker 실행 파일은 있으나 엔진 연결은 실패했다. `supabase`, `pg_dump`, `pg_restore`, `psql`은 현재 PATH에서 발견되지 않았다. C:는 NTFS이고 D:는 exFAT다. C: 암호화 상태 확인은 접근 거부로 실패했다. 충분한 여유 공간이 있다는 사실은 고객정보 보관의 보안을 보장하지 않는다.

### 승인 후 준비 상태

- 사용자가 운영 DB 읽기 전용 export·암호화 보관·격리 복원을 승인했다. 이후 Docker 엔진을 시작했고 기존 PostgreSQL 17 이미지를 이용해 합성 데이터의 암호화·격리 복원을 반복 시험했다. 사용자 전용 ACL이 적용된 NTFS 폴더에는 검토된 도구와 복구 형식 명세만 준비했으며 운영 데이터는 없다.
- PostgreSQL 17 `pg_dump` 소스는 덤프에서 명시적으로 읽기 전용 트랜잭션을 시작한다. 접근에 사용할 DB 계정 자체는 권한이 넓으므로 제한된 서버 역할이라고 주장하지 않는다. 호스트·VM의 페이지파일·최대 절전 암호화는 확인하지 못했다.
- 사용자는 운영 DB 비밀번호를 알고 있다고 답했다. 비밀번호 값과 백업 암호는 받지 않았고, 검토된 로컬 입력 화면은 아직 시작하지 않았다.
- 기존 ego Space 24 연결 호출과 단순 ego nodejs 준비 확인은 응답하지 않아 해당 CLI 보조 프로세스만 종료했다. 기존 Space 연결을 복구한 후 입력 화면과 실제 작업을 진행한다. 실제 운영 export·암호화 백업·복원은 모두 미실행이다. 상세 `receipts/R07_20261128_approved_backup_preflight.json`.

## 백업이 이미 있다면 확인할 항목

담당자가 제공한 **저장 위치와 생성 시각**을 확인한 뒤, 원본 운영 DB의 것인지와 무결성·보관 권한을 검증한다. 고객 데이터·비밀을 채팅이나 Git에 넣지 않는다. 운영을 덮어쓰지 않는 격리 복원으로 스키마·권한·데이터 검증을 마쳐야 비로소 복원 가능성을 판단한다.

## 별도 백업이 없다면 제안하는 범위

1. 사용자가 운영 DB의 읽기 전용 내보내기와 암호화 보관, 별도 격리 환경 복원 시험을 명시 승인했다. 암호화 방식·접근 권한·사용자 복구 암호 관리와 보관 위치를 확인하고 실행한다. D: exFAT에 평문 백업을 만들지 않는다.
2. 운영 DB 연결과 쓰기 방지를 점검하고, Supabase가 권장하는 역할·스키마·데이터 내보내기 범위를 사전에 검토한다. DB 비밀번호나 연결 문자열을 출력·Git·채팅·셸 이력에 남기지 않는다. 현재 Docker 엔진과 필요한 도구 준비는 별도 확인이 필요하다.
3. 복원은 기존 TEST 프로젝트나 운영 프로젝트를 덮어쓰지 않는 폐기용 로컬 격리 DB에서만 수행한다. 복원 대상에서 cron·네트워크 호출·결제사 연동이 실행되지 않도록 사전에 차단하고, 복구된 스키마·핵심 함수·행 수 등 비식별 집계로 검증한다. 데이터 내용이나 자격증명은 증거에 기록하지 않는다.
4. Storage 객체, Edge Functions, 환경 비밀, Auth/SMTP 설정 및 도메인 등은 DB 복원과 별도 범위다. [Supabase 백업 안내](https://supabase.com/docs/guides/platform/backups)와 [플랫폼 DB의 별도 환경 복원 안내](https://supabase.com/docs/guides/self-hosting/restore-from-platform)를 기준으로 빠짐없이 목록화하고, 고객 데이터와 비밀의 보관·삭제 책임자를 정한다.
5. 백업 파일·암호 복구 수단·담당자, 복원 검증 결과와 제한 사항을 실제 근거로 기록한다. 유료 플랜 업그레이드나 원격 프로젝트 생성은 비용과 별도 승인 없이 수행하지 않는다.

위는 검토안이다. 실제 내보내기와 복원은 수행되지 않았고 백업·복원 가능성은 미확인이다.
